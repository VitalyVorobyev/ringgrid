# Migrating from 0.15 to 0.16

Release 0.16 loads only the current target schema, removes dead and
research-only API items, and changes what detection reports. This page
collects the breaking changes by area; each section says what to change.

## Target JSON: only `ringgrid.target.v6` loads

Through 0.15, `TargetLayout::from_json_*` accepted three target schemas and
migrated the older two to the compositional model on load: the flat
`ringgrid.target.v4` (hex coded targets; every `board_spec.json` ever
generated) and `ringgrid.target.v5` (v6 with stored `dots_mm`). 0.16 removes
that migration. A v4 or v5 file now fails with

```text
unsupported target schema 'ringgrid.target.v4' (expected 'ringgrid.target.v6'); convert an older file by loading it with ringgrid 0.15 and saving it again
```

in every entry point that reads a target: `TargetLayout::from_json_str` /
`from_json_file`, `Detector::from_target_json_file*`, the CLIs' `--target`, the
Python `TargetLayout.from_json`, the WASM and C detector constructors.
`TargetValidationError::UnsupportedSchema` lost its `expected` field (the
supported schema is `TARGET_SCHEMA_VERSION`), and
`TargetValidationError::LegacyDotsMismatch` is gone with the v5 check it
belonged to.

**What to update**

Convert each stored target file once, with the last release that still reads
the old schemas:

```rust
// ringgrid 0.15
let target = ringgrid::TargetLayout::from_json_file(std::path::Path::new("board_spec.json"))?;
target.write_json_file(std::path::Path::new("board_spec.json"))?;
```

or, from Python, `ringgrid.TargetLayout.from_json("board_spec.json")` followed by
`Path("board_spec.json").write_text(target.to_spec_json())`, with the 0.15
package. The v6 file describes the same target: the layout, cell positions and
ids are identical (the `id_assignment` of an optimized board is carried over).

The repository's own fixtures (`tools/board/board_spec*.json`,
`testdata/board_ringgrid.json`, `crates/ringgrid/examples/target.json`) were
converted this way. `tools/board/board_spec_extended_opt.json` was a special
case: as a v4 file it implied the base codebook, yet its ids reach 2173, so it
never loaded; it is now a v6 file with `codebook_profile: "extended"`.

`tools/gen_board_spec.py` is removed. Generate the same board with the CLI:

```bash
ringgrid example --name hex_coded --out board.toml
ringgrid gen board.toml --out out --formats json --name ringgrid_200mm_hex
```

`tools/gen_synth.py` now writes a v6 `board_spec.json`, and
`tools/optimize_id_assignment.py` / `tools/board_adjacency_report.py` read and
write v6 (`id_assignment` and `codebook_profile` live under `coding`).

## Removed API items

Each of these was dead or research-only. Code that names them stops
compiling (Rust) or raises `TypeError` / `AttributeError` (Python); stored
JSON that carries the old keys keeps loading.

| Removed | What to do |
|---|---|
| `DetectError::UnsupportedTarget` | Delete the match arm. Every lattice × coding combination detects, so it was never returned; `IncompleteBoard` is the remaining variant (the enum is `#[non_exhaustive]`, keep a `_` arm). |
| `SeedProposalConfig::merge_radius_px`, `SeedProposalConfig::seed_score` (Rust `advanced.seed_proposals`, Python `SeedProposalConfig(...)` keywords, `schemas/detect_config.json`) | Delete the assignments. Neither was ever read: pass 2 uses the pass-1 centres as its only proposals, scored by marker confidence. Config JSON with the keys still loads (unknown keys are ignored). |
| `PhotometricMetrics::covariance_inflation`, `PhotometricMetrics::residual_autocorrelation`, `diagnostics::ResidualAutocorrelation` (Rust and Python) | Research diagnostics; they now live in the photometric study output, behind the `study` feature below. Diagnostics JSON that carries the keys still deserializes. |
| The photometric study API (`photometric_residuals`, `Detector::detect_with_photometric_residuals`, `Detector::detect_adaptive_with_photometric_residuals`) in a default build | Enable the non-default `study` cargo feature. It is hidden from the docs, outside the stable API and not exposed by the bindings. |

## Output changes to check

No code change is needed for these, but results differ from 0.15 and
thresholds tuned against 0.15 output may need revisiting.

- **`DetectedMarker::confidence` is a new score, and low-confidence markers
  are dropped.** Confidence now predicts centre accuracy; its value changes
  for every marker. `DetectConfig::min_confidence` (default `0.03`; Python
  `DetectConfig.min_confidence`, JSON `min_confidence`) drops markers below
  it from the finished result and refits the homography. Set it to `0` to
  keep every marker that passed the detector's gates.
- **Detection fails closed.** IDs, board positions and the homography are
  reported only with a corroborated board placement: a view with a few
  isolated markers or an unreadable code band returns markers with
  `id: None`. With a centre correction configured (the default
  `ProjectiveCenter`), a marker without a perspective-corrected centre is
  not reported; `CircleRefinementMethod::Photometric` recovers most of them.
  Expect fewer markers per image, and no wrong IDs where 0.15 reported them.
- **On coded targets, `DetectedMarker::id` is the ID of the grid cell the
  ring sits in.** A misread code band is overridden by its cell; the code
  band's own reading is still in `diagnostics.markers[].decode`, so the two
  can differ.
- **With `CircleRefinementMethod::Photometric`, the homography is refit from
  the refined centres**, together with `DetectionDiagnostics::ransac` and
  each marker's `fit.h_reproj_err_px`.
